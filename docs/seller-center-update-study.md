# دراسة تحديث تطبيق السلر سنتر — Seller Center

**التاريخ:** 2026-08-23
**النطاق:** تطبيق البائع (Flutter) + واجهات API الخاصة بالبائع في الباك (Laravel — مشروع Pharmacy)
**الهدف:** تحديث التطبيق ليستفيد من كل مميزات الباك، وتحديث واجهته بالكامل.

---

## الملخص التنفيذي

1. **تغطية الـ API الحالية ممتازة:** التطبيق يستهلك ~144 من أصل 148 endpoint في `api/v3/seller`. الفجوة الحقيقية ليست في الـ API الحالي، بل في **ميزات الباك الجديدة (حزمة Marketplace — Phase 3)** الموجودة في لوحة البائع "ويب" فقط وبلا أي API موبايل: مركز البائع، بطاقة الأداء، التحقق KYC، السحوبات عبر الدفتر المحاسبي (Ledger Payouts)، طاقم العمل والأدوار، التحليلات، التقارير.
2. **الواجهة:** يوجد نظام تصميم زجاجي حديث (`AppGlass` + خط Cairo + Material 3 + نظام حركة موحّد) لكنه مطبَّق بشكل غير متساوٍ، والأهم: **يوجد قشرتان تنقّل متنافستان** (`DashboardScreen` و `NavBarScreen`) وقائمة Bottom Sheet فيها +20 بند تعمل كتنقّل فعلي. إعادة بناء الـ IA (بنية التنقل) هي أساس تحديث الواجهة.
3. **حواجز النشر:** هوية التطبيق ما زالت هوية القالب الأصلي (`com.sixamtech.sixvalley.seller`)، والتوقيع debug، ومشروع Firebase — كلها موثقة في `MIGRATION.md` ويجب حسمها قبل أي إصدار متجر.

الخطة المقترحة: 6 مراحل، تبدأ بمكاسب سريعة من endpoints جاهزة وغير مستخدمة، ثم توحيد القشرة وتحديث الواجهة، ثم بناء API + شاشات لحزمة Marketplace.

## 1. الوضع الحالي — التطبيق

### 1.1 الأرقام

| البند | القيمة |
|---|---|
| ملفات Dart | 630 ملف / ~99,600 سطر |
| ميزات (features) | 33 وحدة feature-first |
| شاشات | 84 شاشة |
| Providers (state) | 44 ChangeNotifierProvider |
| اللغات | عربي (افتراضي) + إنجليزي — 1300 مفتاح لكل لغة، بفحص تكافؤ في CI |
| Flutter | 3.47.0 stable (Dart 3.11) مثبّتة في CI — AGP 8.13.2 / Kotlin 2.2.21 |
| الإصدار | pubspec: `1.1.0+6` (ثابت `appVersion = 16.2.1` موروث من القالب) |

### 1.2 البنية

```
lib/features/<feature>/
  controllers/        # ChangeNotifier
  domain/
    models/           # نماذج JSON
    repositories/     # Dio + AppConstants URIs
    services/         # منطق وسيط
  screens/ , widgets/
```

بنية نظيفة ومتسقة (repository ← service ← controller ← screen). الشبكة عبر `Dio` مع `DioClient` مركزي، والتخزين عبر `shared_preferences` + `flutter_secure_storage`.

### 1.3 نظام التصميم الحالي

- **`AppGlass`** (ThemeExtension): توكنات زجاج كاملة — tint/solidTint/border/highlight/blur + 3 مستويات ظل + خلفية Ambient + تدرجات علامة ودلالية (نجاح/تحذير/خطر/معلومة) + ألوان shimmer. يعمل في الوضعين الفاتح والداكن.
- **الخط:** Cairo موحّد عربي/لاتيني (4 أوزان) + Roboto للمواضع القديمة.
- **الحركة:** نظام موحّد موثق في `ANIMATION_SYSTEM_GUIDE.md` عبر `flutter_animate` (`animateSectionEntrance`، بلا bounce/elastic).
- **مكونات أساسية:** ~40 basewidget (أزرار، حقول، bottom sheets، قوائم lazy مع pagination، shimmers، حوارات).

**المشكلة:** التطبيق خليط بين شاشات محدّثة على `AppGlass` وشاشات ما زالت على أنماط القالب القديم (ألوان مباشرة، `robotoRegular`, بطاقات مسطحة). التحديث الكامل = تعميم النظام الموجود، لا اختراع نظام جديد.

### 1.4 مشاكل بنية التنقل (IA) — أهم عيب في الواجهة

- **قشرتان متنافستان:**
  - `DashboardScreen`: تبويبات (الرئيسية / طلباتي / الاسترجاع / قائمة) مع IndexedStack.
  - `NavBarScreen`: قشرة ثانية كاملة لعالم POS (POS / طلباتي / المنتجات / قائمة) مع زر ماسح باركود عائم — تُفتح **من داخل** القائمة كبند "POS"، فيصبح عند المستخدم شريطا تنقل سفليان مختلفان حسب المكان الذي وصل منه، وشاشة "طلباتي" تظهر في القشرتين.
- **القائمة (Bottom Sheet) هي التنقل الفعلي:** +20 بند بلا تجميع منطقي (متجري، منتجات، كوبونات، مندوبين، محفظة، ضرائب، سياسات...).
- ديون تسمية: فلاتر التحليلات في الرئيسية تُدار من `BankInfoController`؛ `color_resources.dart` فارغ؛ `refund_uri.dart` سطر واحد.

### 1.5 جاهزية الإصدار (من `MIGRATION.md`)

| الحاجز | الحالة |
|---|---|
| Keystore للتوقيع | غير منشأ — release يسقط على توقيع debug مع تحذير |
| applicationId / bundle id | ما زال `com.sixamtech.sixvalley.seller` (هوية القالب) |
| مشروع Firebase خاص | لم يُنشأ (google-services للقالب) |

**الثلاثة لا رجعة فيها بعد النشر — يجب حسمها في المرحلة 0.**

ملاحظات:

### 2.2 ميزات الباك الجديدة — حزمة Marketplace (Phase 3) — **ويب فقط**

خدمات جاهزة ومختبرة في `app/Services/Marketplace/`، معروضة فقط في لوحة البائع الويب (`routes/vendor/routes.php`)، **بلا أي API موبايل**:

| الميزة | الخدمة في الباك | ماذا تقدّم |
|---|---|---|
| مركز البائع (Hub) | `SellerCenterService::overview()` | نظرة واحدة: تحقق + أداء + مالية + SLA |
| بطاقة الأداء | `SellerScorecardService::scorecard()` + `deriveTier()` | معدلات التنفيذ/الإلغاء/الإرجاع/الاسترداد، التقييم، المخالفات، وتصنيف صحّي (new/good/watch/at_risk) |
| التحقق KYC | `SellerVerificationService` | أنواع مستندات مطلوبة، رفع، حالة كل مستند، أهلية السحب |
| السحوبات عبر الدفتر | `PayoutService` + `VendorLedger` | أرصدة (متاح/معلّق/محجوز)، قابل للسحب، طلب سحب يحجز الرصيد، إلغاء، رقابة مزدوجة، فترة تبريد بعد تغيير بنكي |
| طاقم العمل والأدوار | `SellerPermissionService` + `SellerStaff/SellerRole` + `staff-auth` (ويب) | أدوار بصلاحيات، موظفون يسجلون دخولا بحسابهم ويعملون باسم البائع |
| اتفاقية مستوى الخدمة | `SlaService` | عتبات، خروقات مفتوحة |
| التحليلات | `Analytics/Reporting::forVendor(window)` | مشاهدات، منتجات، نوافذ زمنية |
| أنشطة لحظية | `DashboardController::getRealTimeActivities()` | طلبات جديدة غير مقروءة + طلبات restock |
| التقارير والتصدير | Product/Order/Transaction ReportControllers | تقارير منتجات/مخزون/طلبات/معاملات مع Excel وPDF |
| استيراد جماعي للمنتجات | `bulk-import` | رفع ملف منتجات |

**هذه هي "مميزات الباك" التي يريدها التطبيق — وكلها تحتاج بناء endpoints جديدة في `v3/seller` (الخدمات جاهزة، فالكلفة أساسًا Controllers + Resources) ثم شاشات في التطبيق.**

## 3. تحليل الفجوات

### فجوة A — endpoints غير مستخدمة (مراجَعة بعد فحص الكود — المرحلة 1 نُفّذت)

الفحص العميق غيّر الخلاصة الأولية: الأربعة "غير المستخدمة" إما **مكررة** أو **أسوأ** من المستخدَم فعليًا:

| Endpoint | الحكم بعد الفحص | ما نُفّذ بدلًا منه |
|---|---|---|
| `GET monthly-earning` + `monthly-commission-given` | **مكرر** — نفس بيانات `get-earning-statitics?type=yearEarn` المستخدم أصلًا، وبصيغة أسوأ (سلسلة نصية بفاصلة زائدة) | أُضيف رسم الأرباح السنوي لشاشة المحفظة بإعادة استخدام endpoint الموجود |
| `GET products/list` | **تراجُع** — بلا pagination ولا بحث، وحقول JSON خام بلا تنسيق؛ المسار الحالي `{seller_id}/all-products` أغنى بكثير | أُصلحت أخطاء فعلية: الصفحة 2+ كانت تفقد الفلاتر والبحث والفرز؛ pageSize خاطئ (10 مقابل limit=20)؛ تطبيق الفلتر كان يبدأ من الصفحة الحالية بدل الأولى |
| `GET pos/get-categories` | التطبيق يستخدم `/seller/categories` المكافئ أصلًا | أُصلح الخطأ الفعلي: فلتر تصنيفات POS كان يضيع عند التمرير والبحث والتحديث — الآن يثبت |

**درس معماري:** بعض endpoints الـ v3 القديمة بقايا نسخ سابقة — قبل "الاستفادة" من أي endpoint غير مستخدم يجب فحص جودته مقابل الموجود.

إصلاحات إضافية نُفّذت بنفس الدفعة: خطأ عرض بالرسم البياني (خط «الأرباح» كان يعرض العمولة والعكس، وألوان الدليل معكوسة)، وطلب مكرر لإحصائيات الطلبات عند الإقلاع.

### فجوة B — ميزات باك بلا API (تحتاج عمل باك + تطبيق)

مرتبة حسب القيمة للبائع:

| # | الميزة | عمل الباك المطلوب (v3/seller) | عمل التطبيق المطلوب |
|---|---|---|---|
| 1 | **مركز البائع** | `GET seller-center/overview` (يغلّف `overview()`) | رأس جديد للشاشة الرئيسية: شارة التصنيف، حالة التحقق، الرصيد القابل للسحب، خروقات SLA |
| 2 | **بطاقة الأداء** | `GET scorecard` | شاشة أداء: المؤشرات الثمانية + شرح التصنيف وكيف يتحسن |
| 3 | **التحقق KYC** | `GET verification` + `POST verification/submit` (multipart) | شاشة مستنداتي: المطلوب/المرفوع/الحالة/سبب الرفض + رفع من الكاميرا |
| 4 | **المحفظة v2 (Ledger)** | `GET payouts/balances` + `GET payouts` + `POST payouts` + `POST payouts/{id}/cancel` | إعادة بناء المحفظة: متاح/معلّق/محجوز، طلب سحب مربوط بالقابل للسحب، تنبيه فترة التبريد وأهلية KYC |
| 5 | **التحليلات** | `GET analytics?range=` (يغلّف `forVendor`) | شاشة تحليلات: مشاهدات المتجر والمنتجات حسب نافذة زمنية |
| 6 | **الأنشطة اللحظية** | `GET real-time-activities` | بطاقة تنبيهات حية بالرئيسية (طلبات جديدة، restock) + بادجات |
| 7 | **التقارير** | `GET report/products`, `GET report/orders`, `GET report/transactions` (JSON + رابط ملف) | شاشة تقارير بمشاركة الملفات (يوجد `report_export_helper` جاهز) |
| 8 | **طاقم العمل والأدوار** | الأكبر: أدوار CRUD + موظفون CRUD + **دخول موظف بالـ API** (توسيع `seller_api_auth` بنطاق صلاحيات) | شاشات فريق العمل + إخفاء أزرار الواجهة حسب الصلاحية |
| 9 | استيراد جماعي | منخفض القيمة على الموبايل | مؤجّل — يبقى ويب |

> ملاحظة معمارية: كل endpoints الفجوة B تغلّف خدمات موجودة — **ممنوع تكرار المنطق** (قاعدة "Web وAPI بنفس المنطق" مطبقة أصلًا في المشروع).

### فجوة C — تنظيف داخل التطبيق

1. توحيد القشرتين في قشرة واحدة (القسم 4).
2. نقل حالة فلاتر التحليلات من `BankInfoController` إلى controller باسم صحيح.
3. حذف `color_resources.dart` الفارغ ودمج `refund_uri.dart`.
4. توحيد رقم الإصدار (قراءة من `package_info_plus` بدل ثابت القالب `16.2.1`).
5. حسم حواجز النشر الثلاثة (1.5).

## 4. خطة تحديث الواجهة الكاملة

### 4.1 المبادئ

- **قشرة واحدة، لغة تصميم واحدة:** `AppGlass` هو النظام؛ أي شاشة لا تقرأ منه تُحدَّث إليه. RTL أولًا، Cairo فقط (إخراج Roboto تدريجيًا).
- **لا يُكسر أي سلوك موجود:** التحديث شاشة-بشاشة خلف نفس الـ controllers.
- حالات موحّدة لكل شاشة: shimmer (موجود)، فراغ (`no_data_screen`)، خطأ + إعادة محاولة.

### 4.2 بنية التنقل الجديدة (IA)

شريط سفلي واحد بخمسة تبويبات + زر ماسح عائم:

| تبويب | المحتوى |
|---|---|
| **الرئيسية** | مركز البائع (جديد) + أنشطة لحظية + إحصائيات الطلبات + الرسوم (يومي/شهري الجديد) + نفاد المخزون + الأكثر مبيعًا |
| **الطلبات** | القائمة الحالية + الاسترجاع كتبويب علوي داخلها (بدل تبويب سفلي مستقل) |
| **POS** | شاشة POS الحالية + الماسح كإجراء أساسي (يبقى الزر العائم) |
| **المنتجات** | قائمة المنتجات بالفلاتر الجديدة (`products/list`) + إضافة منتج + restock + clearance كمداخل علوية |
| **المزيد** | القائمة الحالية معاد تنظيمها في أقسام: متجري / المبيعات والتسويق / التوصيل / المالية (محفظة v2، معلومات الدفع، ضرائب) / الفريق (جديد) / الإعدادات والسياسات |

يُحذف `NavBarScreen` كقشرة مستقلة (يصبح تبويب POS داخل القشرة الموحدة)، ويُعاد استخدام تصميمه الزجاجي للشريط الموحّد.

### 4.3 دفعات إعادة التصميم (84 شاشة)

| الدفعة | الشاشات | العمل |
|---|---|---|
| B1 — القشرة والرئيسية | dashboard, nav_bar, home + widgets | دمج القشرتين، رأس مركز البائع، أنشطة لحظية، رسم شهري |
| B2 — الطلبات | order, order_details, order_edit, refund (9 شاشات) | بطاقات زجاجية موحدة، شريط حالة زمني (timeline)، دمج الاسترجاع |
| B3 — المنتجات | product, addProduct, product_details, restock, clearance, barcode (15) | فلاتر `products/list`، معالج إضافة منتج بخطوات أوضح، توحيد نماذج الإدخال |
| B4 — POS | pos (7) | تحديث بصري فقط — المنطق حسّاس (offline outbox) |
| B5 — المالية | wallet, transaction, bank_info, vat (6) | محفظة v2 على الدفتر، بطاقات أرصدة بالتدرجات الدلالية |
| B6 — الباقي | chat, delivery_man (12), review, coupon, shop, profile, settings, auth, notification | تعميم النظام + شاشات الفريق الجديدة |

### 4.4 مكوّنات جديدة مطلوبة

- `TierBadge` (new/good/watch/at_risk بالتدرجات الدلالية الموجودة)
- `LedgerBalanceCard` (متاح/معلّق/محجوز)
- `DocumentUploadTile` (KYC: الحالة + سبب الرفض)
- `ActivityTicker` (الأنشطة اللحظية)
- `SegmentedFilterBar` موحّد للفلاتر (منتجات/طلبات/تقارير)

**الإجمالي التقريبي: 10–15 أسبوع عمل.** المراحل 1 و2 تُنتج تطبيقًا محدّث الواجهة بالكامل حتى لو تأجلت 3 و4.

## تشخيص عطل تسجيل الدخول (2026-08-23)

**العرَض:** التطبيق لا يدخل — لا تظهر شاشة تسجيل الدخول أصلًا.

**السبب الجذري:** شاشة البداية تفحص الإصدار قبل أي توجيه:
- السيرفر ينشر `seller_app_version_control` = **14.1** (لوحة الأدمن ← إعدادات الأعمال ← إعدادات التطبيق)
- `pubspec.yaml` كان **1.1.0** → `AppVersion.isUpdateRequired('14.1')` = صحيح → `UpdateScreen` تستبدل البداية، ولا طريق للوصول لنموذج الدخول.

الثابت القديم `AppConstants.appVersion = '16.2.1'` كان يخفي المشكلة (أكبر دائمًا من 14.1). حين صار الفحص يقرأ إصدار الحزمة الحقيقي، سقط خط الإصدار 1.x تحت الحد المطلوب وأُغلقت البوابة على الجميع. وضع الصيانة كان مطفأً، و endpoint الدخول نفسه سليم (يرد 401 صحيحًا على بيانات خاطئة).

**الإصلاح:** رفع الإصدار إلى `16.2.2+7`، واختبار انحدار (`test/app_version_gate_test.dart`) يُفشل البناء إذا نزل الإصدار تحت الحد المنشور، وتوثيق الاقتران في `MIGRATION.md`.

**البديل:** خفض الحد بلوحة الأدمن إلى `1.1.0` والإبقاء على خط إصدار التطبيق الخاص — عندها يجب تعديل الثابت في ملف الاختبار أيضًا.

## دروس من مراجعة شاشات المال (2026-08-23)

المراجعة العدائية لشاشتَي KYC والسحوبات (25 وكيلًا) أكدت 18 ملاحظة تعود لـ7 عيوب فعلية — كلها أُصلحت قبل الدفع. الأهم:

| العيب | لماذا يهم |
|---|---|
| **رسائل الرفض لم تكن تظهر إطلاقًا** | Dio يرمي استثناءً على 403، فلا يوجد `response` لقراءة السبب منه — السبب موجود أصلًا في `ApiResponse.error` بعد أن يستخرجه `ApiErrorHandler`. كان البائع يرى فشلًا عامًّا بدل «الرصيد غير كافٍ» أو «التحقق مطلوب» |
| **رسائل الخطأ تظهر خضراء** | `showCustomSnackBarWidget` يتجاهل `isError` تمامًا — التنسيق يأتي من `sanckBarType` وافتراضه `success`. رفض السحب كان يظهر بعلامة ✓ خضراء |
| **جدول الأرصدة لا يجمع** | الدفتر يعيد أربعة أرصدة تجمع بالضبط على الإجمالي؛ عرض ثلاثة منها تحت خط فاصل يدّعي جمعًا خاطئًا — كان ينقص 200 من بيانات حقيقية بلا أي تفسير |
| **الملف المرفوع يتسرّب بين الفتحات** | الملف المختار يعيش على متحكّم مشترك؛ إغلاق الورقة بالسحب يتركه، فالإرسال التالي يرفع مستند المرة السابقة صامتًا |
| **انهيار القائمة المنسدلة** | `_documentType ??= types.first` يُثبَّت من قائمة احتياطية، فإذا وصلت قائمة الخادم بأنواع أخرى صار للقائمة قيمة غير موجودة ضمن خياراتها → استثناء |
| **خلط العملة بمسار المال** | الرصيد يُعرض محوَّلًا بينما زر «الأقصى» والفحص يستخدمان الرقم الخام؛ صُحّح ليعمل كله بعملة العرض مع تحويل عكسي قبل الإرسال، والسقف يُقتطع لا يُقرَّب |

اختبارات عقود تثبّت هذا: حمولات ملتقطة حرفيًا من خادم حيّ + التحقق من أن الأرصدة الأربعة تجمع على الإجمالي.

## الربط مع Monitoring / Analytics / Developer Portal

| القسم | الحالة | ما نُفّذ |
|---|---|---|
| **Monitoring** | تلقائي | `MonitorRequest` مسجّل عالميًا وفي مجموعة `api`، فكل endpoint جديد يدخل قياسات الطلبات (زمن، أخطاء، p95/p99، تتبّع، استعلامات بطيئة) بلا تسجيل يدوي. لا توجد قائمة مسارات مراقَبة. |
| **Analytics** | ✅ رُبط | حدثان جديدان `payout_requested` و`kyc_submitted` في الكتالوج + بابان في `Analytics.php`، ومُسجَّلان **داخل الخدمات** (`PayoutService`, `SellerVerificationService`) فيلتقطهما الويب والتطبيق معًا. يحملان `vendorId` فيظهران بصفحة تحليلات البائع. اختبار الحارس `EveryEventCanFireTest` يمرّ. |
| **Developer Portal** | ✅ رُبط | الاكتشاف تلقائي من جدول المسارات، لكن الوصف كان آليًا. أُضيفت `#[ApiDoc]` للثمانية جميعًا (ملخص، وصف، جمهور `vendor_app`، مجموعة، `emits`) → صارت `documented=Y` بدل «غير مصنّفة». ملاحظة: `POST payouts` و`verification/submit` محظورتان دائمًا في وحدة التجربة (`ConsoleGuard::NEVER_WRITE`) وهذا مقصود. |
| **Audit** | ✅ ثغرتان أُصلحتا | (1) طلب السحب من البائع لم يكن له سطر تدقيق إطلاقًا — السجل يرى فقط موافقة الأدمن لاحقًا؛ أُضيف `payout.requested`. (2) **كل قرارات KYC كانت تُدقَّق في الفراغ**: معامل `?AuditLogger $audit = null` لا تحقنه الحاوية أبدًا، فكان `$this->audit?->record()` عملية صامتة — لم يُكتب أي `seller.kyc_submitted/approved/rejected` منذ البداية. صار الحل يُحلّ كسولًا. |

**تحذير مفتوح:** نفس نمط `?AuditLogger $audit = null` موجود في 8 خدمات Marketplace أخرى (`BatchService`, `InventoryService`, `PurchaseOrderService`, `ExchangeRateService`, `ReturnLogisticsService`, `WarehouseService`, `FulfillmentService`, `SlaService`) — تدقيقها معطّل على الأرجح بنفس الطريقة ويستحق مراجعة منفصلة.
